# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Writing rules (apply to everything you produce)

- **Language: English for code, French for player-facing UI.** Variables, identifiers, type names, comments, doc strings, README, CLAUDE.md, commit messages, file names, log strings (server-side `Log.Info`, `Log.Warning`, etc.), and developer-facing error messages stay in **English**. **Player-facing strings** (Razor templates rendered in-game, on-screen labels, button captions, form labels, validation messages surfaced to a connected client through the UI, chat broadcasts shown to players) are in **French**. The split is "would a non-developer player ever read this?". If yes, French. Otherwise English. The user converses in French, so reply to the user in French in chat.
- **Never use long dashes.** No em dash (`—`, U+2014). No en dash (`–`, U+2013). Use the ASCII hyphen-minus `-` only, and only where a hyphen genuinely fits (compound words, ranges in code). When you would have reached for an em dash for a parenthetical or a clause break, rewrite with a comma, period, colon, semicolon, or parentheses instead. This rule is absolute and applies to code, comments, docs, commit messages, and chat replies.
- **Author header on every new code file.** Any code file you create must start with an `@author Epyi` header in the file's native comment syntax. TS/JS/C#/Razor: `/** @author Epyi */`. SQL/Python: `-- @author Epyi` (or `# @author Epyi`). Shell/Dockerfile/yaml: `# @author Epyi`. Skip on JSON (no comments) and Markdown (renders as text). Only on files you create, do not retrofit upstream Facepunch Sandbox files unless explicitly asked.

## Project

**Mirage** is a roleplay gamemode for **s&box** (sbox.facepunch.com), forked from Facepunch's official Sandbox game and being progressively rebuilt into a FiveM-style RP server. Author: `lets-pop`. Project descriptor is `mirage.sbproj` (`Org=lets-pop`, `Ident=mirage`); startup scene is still `scenes/sandbox.scene` (asset rename will come later as the gamemode evolves). Multiplayer (32 max), tick rate 50, host-authoritative.

The code in `Code/` and the assets in `Assets/` are still largely the original Sandbox base. Most existing files are upstream code, and the RP-specific systems will be built on top, mostly as new components and systems plugged into the existing event interfaces.

## Building and running

There is no command-line build. s&box compiles the project from the editor:

- Open the directory as a project in the **s&box editor** to build, run, and hot-reload.
- `*.csproj`, `*.sln`, `obj/`, `bin/`, `.sbox/` are all generated by the editor and gitignored. Do not commit them and do not hand-edit.
- There is no test suite.

When making changes you can verify only by reading the code. Flag any change that needs in-editor verification rather than claiming success.

## Style (enforced by `.editorconfig`)

C# uses **tabs** (size 4), **CRLF**, final newline. Braces always go on a new line (`csharp_new_line_before_open_brace = all`). Spaces **inside** method-call parens (`foo( a, b )`) but no space between name and `(`. Expression-bodied accessors, properties, lambdas, and indexers preferred; expression-bodied methods and constructors not. `using` directives go **outside** the namespace. Match the existing style precisely. Diffs that change whitespace get rejected.

## Globally imported usings

`Code/Assembly.cs` and `Editor/Assembly.cs` declare `global using` for `System`, `Sandbox`, `Sandbox.Diagnostics`, `System.Linq`, `System.Threading.Tasks`, `System.Collections.Generic` (and `Editor`, `Sandbox.UI` in editor). Don't add per-file usings for these. Most game code lives without an explicit `namespace` (top-level), with `namespace Sandbox;` used only where engine extension points require it.

## Architecture

### Code organisation

- `Code/`: gameplay (compiled into the game assembly).
- `Editor/`: editor-only code, not shipped.
- `Assets/`: scenes, prefabs, materials, sounds, UI textures, weapon defs, etc. `Assets/scenes/sandbox.scene` is the entry scene.
- `Localization/`, `ProjectSettings/`: engine-managed.
- `Api/`: Node.js + TypeScript backend (Fastify + MariaDB). See "Backend API" section below. Not part of the s&box build, not bundled when publishing.

Within `Code/`, the major subsystems are: `Player/`, `GameLoop/` (GameManager etc.), `Game/` (Weapon base classes, Entity types, BanSystem, ControlSystem, PostProcessing, Sound), `Weapons/` (concrete weapons), `Spawner/`, `Items/`, `Cleanup/`, `Save/`, `Map/`, `Npcs/`, `UI/` (Razor), `Utility/`, `FreeCam/`.

### Component / Scene model (s&box)

Code is organised around `Component` subclasses on `GameObject`s in a `Scene`. Lifecycle hooks: `OnAwake`, `OnStart`, `OnUpdate`, `OnFixedUpdate`, `OnDestroy`. Properties shown in the editor use `[Property]`; `[RequireComponent]` auto-adds dependencies.

Cross-cutting systems live as `GameObjectSystem<T>` singletons, accessed via `Scene.Get<T>()` or the static `T.Current`. Examples: `GameManager`, `SaveSystem`, `CleanupSystem`, `UndoSystem`, `BanSystem`, `LimitsSystem`, `FreeCamGameObjectSystem`. New cross-cutting state usually belongs in a system, not a Component.

### Networking model

Host-authoritative. Three RPC attributes you'll see everywhere:

- `[Rpc.Host]`: client to host call (host runs the body). Always check `Rpc.Caller` matches the expected owner before mutating anything: `if ( Rpc.Caller != Network.Owner ) return;`.
- `[Rpc.Owner]`: host to owning client.
- `[Rpc.Broadcast]`: host to everyone (use `NetFlags.HostOnly | NetFlags.Reliable` for state-change broadcasts).

Replicated fields use `[Sync( SyncFlags.FromHost )]` (host writes, clients read). Mutating a synced field on a client is a bug, route through an `[Rpc.Host]` setter (see `GameManager.ChangeProperty`). After server-side mutations not captured by `[Sync]` (e.g. material override changes), call `gameObject.Network?.Refresh()`.

Spawn flow: host creates the GameObject, calls `go.NetworkSpawn( ownerConnection )`. `Player.IsLocalPlayer` is `!IsProxy`.

### Event system, two flavours

The codebase uses two parallel `ISceneEvent<T>` interfaces, both partial classes wrapping nested interfaces:

- **`Local.IPlayerEvents`**: fired only on a specific GameObject hierarchy, via `Local.IPlayerEvents.PostToGameObject( go, x => x.OnSpawned() )`. Implement on a Component to react to *its own* player's events.
- **`Global.IPlayerEvents`**: fired across the entire scene, via `Global.IPlayerEvents.Post( x => x.OnPlayerSpawned( player ) )`. Implement on a system to react to *any* player.

The same split exists for `Global.ISpawnEvents`, `Global.ISaveEvents`, `ICleanupEvents`, `IPhysgunEvent`, `IToolgunEvent`, `IToolActionEvents`, `ISpawnEvents`. Many events use a mutable event-data class with a `Cancelled` flag so listeners can veto (e.g. `PlayerDamageEvent`, `PlayerPickupEvent`, `PlayerRespawnEvent`).

Defining new events: add to one of these interfaces (fire from the producer, implement on the consumer). Don't invent a third event mechanism.

### Partial-class feature split

`Player`, `GameManager`, and `BaseCarryable` are split across many files by feature: `Player.cs`, `Player.Camera.cs`, `Player.Ammo.cs`, `Player.ConsoleCommands.cs`, `Player.Undo.cs`, `Player.Loadout.cs`, `GameManager.Spawn.cs`, `GameManager.Water.cs`, etc. When adding a new feature area to one of these, make a new `*.cs` partial file rather than growing the main file.

### Spawning / ISpawner

Anything placeable through the spawn menu implements `ISpawner` (display name, icon, bounds, async loading, preview rendering, host-side `Spawn`). Concrete implementations: `PropSpawner`, `EntitySpawner`, `MountSpawner`, `DuplicatorSpawner`, `SpawnerWeapon`. Spawning fires `Global.ISpawnEvents.OnSpawn` (cancellable) then `OnPostSpawn`. `LimitsSystem` plugs in here for per-player caps (`sb.limit.props` etc., declared via `[ConVar]`).

### Weapons

Inheritance chain: `Component` to `BaseCarryable` (inventory item, view/world model) to `BaseWeapon` (ammo, reloading) to `BaseBulletWeapon` / `MeleeWeapon`. Concrete weapons live under `Code/Weapons/<Name>/`. View and world models are separate `WeaponModel` GameObjects driven by `BaseCarryable.ViewModel.cs` / `WorldModel.cs`. `IronSightsWeapon` is a mixin-style helper.

### GameResource definitions

`ScriptedEntity` (`.sent`) and `ScriptedEmitter` are `GameResource`s editable in-editor. They wrap a `PrefabFile` plus metadata. The `IDefinitionResource` interface (`Title`, `Description`) marks resources surfaced in pickers; `MetadataAttribute` is a property attribute used by the editor to filter `GameResource` pickers by tag.

### UI

UI is **Razor** (`.razor` + `.razor.scss` + optional `.razor.cs`) under `Code/UI/`. The HUD root is `Hud.scss`. The spawn menu lives under `UI/SpawnMenu/` and discovers tabs via `ISpawnMenuTab` / `IUtilityTab` (any Component implementing these auto-appears as a tab, drop a new file, no registration needed).

### Save, cleanup, undo

- `SaveSystem` (`Code/Save/`) snapshots scene **diffs** from the original. Save format version is `CurrentSaveVersion = 2`. Bumping it invalidates old saves. Components implementing `Global.ISaveEvents.AfterLoad` get a callback after load (e.g. `Player` re-applies clothing).
- `CleanupSystem` (`Code/Cleanup/`) tracks which GameObjects existed in the baseline scene; "cleanup" removes spawned objects and restores destroyed baseline ones. Players are excluded.
- `UndoSystem` is per-SteamId, capped at `MaxUndoSteps = 128`. Always call `UndoSystem.Current?.RemovePlayer(steamId)` on disconnect (see `GameManager.OnDisconnected`).

### Console vars and commands

Tunables use `[ConVar( "sb.something", ConVarFlags... )]` on a static property; commands use `[ConCmd( "name" )]` on a static method. `ConVarFlags.Replicated | ConVarFlags.Server | ConVarFlags.GameSetting` is the standard for server-side gameplay limits. Cheat/dev commands use `ConVarFlags.Cheat`. `Player.ConsoleCommands.cs` and `*.ConVars.cs` files are the conventional homes.

## Backend API (`Api/`)

The s&box code sandbox blocks raw SQL drivers and sockets, so the gamemode cannot speak SQL directly. Persistent state for RP features (money, inventory, position, jobs, properties) lives behind an HTTP API in `Api/`, written in Node.js + TypeScript with Fastify and MariaDB. The s&box host calls it via `Sandbox.Http`. The API is meant to run as a sidecar process next to the s&box dedicated server.

- **Not in the gamemode build.** `Code/mirage.csproj` only scans `Code/`, so `Api/` is invisible to the s&box compiler. Publishing the gamemode does not bundle `Api/` either (the `Resources` globs in `mirage.sbproj` do not match it).
- **Stack.** Node 20+, TypeScript strict, Fastify 5, `fastify-type-provider-zod`, `mysql2/promise`, single `import.sql` for the schema (no migration runner). No ORM. Repository, service, route layers separated.
- **Auth.** Single shared bearer token (`API_BEARER_TOKEN` env var). The s&box host sends `Authorization: Bearer <token>` on every call. Constant-time comparison. The API is meant to bind on a private interface (`127.0.0.1`) and stay behind the firewall.
- **Data model.** OOC and IC are split. `players` (OOC) holds Steam account identity and IP history. `characters` (IC, one row per RP character, owned by a player via `steam_id` and indexed by `slot`) holds position and timestamps. `accounts` (one row per wallet per character: `account_id`, `amount`) and `character_inventory` (one row per occupied slot: `slot`, `item_id`, `quantity`, optional `metadata` JSON) hang off a character, not off a player.
- **Idempotency by design.** Character creation is keyed on `(steam_id, slot)` so a replayed POST returns 409 instead of duplicating. All other writes are slot-keyed or row-keyed upserts, so retries converge.
- **Source of truth.** When a gameplay system needs persistent state, the API is authoritative. The host holds an in-memory cache of an active character, syncs it back via the API as state changes, and flushes on disconnect. Do not invent parallel local-file persistence.

See `Api/README.md` for setup, run, endpoints, and deployment notes.

## Commit conventions

When making commits in this repo:

- **Messages in English**, conventional-commits format `type(scope): description` (e.g. `feat(player): add RP identity sheet`, `chore(project): rename to Mirage`, `docs(readme): clarify build section`).
- **Never add a `Co-Authored-By` trailer.** This overrides the default Claude Code commit template.
- **Prefer multiple small commits** split by logical concern over one large bundled commit.
- **Don't `git add -A` or `git add .`.** Add specific paths.
- **Don't push** unless explicitly asked.
- **No long dashes** in commit messages either (per the writing rules above).

## Security and authority checks

Any `[Rpc.Host]` that mutates a GameObject must verify the caller can act on it. The typical pattern is `go.HasAccess( Rpc.Caller )` (uses the `Ownable` component) or `Rpc.Caller != Network.Owner` for player-self actions. `GameManager.DeleteInspectedObject` and `BreakInspectedProp` are good references. Don't trust client-supplied paths or identifiers without bounds-checking.
